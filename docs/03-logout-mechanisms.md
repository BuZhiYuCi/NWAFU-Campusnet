# 两种"下线"机制的实测差异（重要）

本文记录 Phase 3 验收时发现的一个关键事实：**在这套校园网上，
`action=logout` 无法真正让设备离线，只有 `rad_user_dm` 可以。**

原始实验数据见 `docs/phase3-verify.md`（"对照实验"两节）。

---

## 1. 现象

同一台机器（`10.128.96.98`），先后用两种机制注销，随后每 2 秒观察一次：

### 1.1 `action=logout`（门户网页上"注销"按钮走的就是这条）

| t(s) | rad_user_info | 本机在设备列表里 | 外网 TCP 可连 | 访问百度 |
| --- | --- | --- | --- | --- |
| 0 | speed_limit_error | **MAC认证 / MAC auth**（时间戳＝注销那一秒） | ✓ | 200（真百度） |
| 3 ~ 32 | 同上 | 同上 | ✓ | 200（真百度） |

**结论：一秒钟都没断网。** 注销请求服务端返回 `error: ok`（确实受理了），
但准入设备在同一秒用 **MAC 免认证**把这台设备重新认证上线，
设备列表里立刻出现一条 `client_type=6 / os_name="MAC auth"` 的会话。

### 1.2 `rad_user_dm`（unbind=1，踢指定 IP）

| t(s) | rad_user_info | 本机在设备列表里 | 外网 TCP 可连 | 访问百度 |
| --- | --- | --- | --- | --- |
| 0 | speed_limit_error | **不在列表** | ✗ | 200（门户拦截页，非真百度） |
| 6 ~ 67 | 同上 | 不在列表 | ✗ | 同上 |

**结论：真正离线，且 67 秒全程保持离线。**

（HTTP 返回 200 是准入门户的拦截页面，不是真的访问到了百度；
直接测 TCP 才是可靠判据——这也是本次实验同时记录两项的原因。）

---

## 2. 原因

`rad_user_dm` 的参数是 **`unbind=1`**，字面意思就是"解绑"：
它在注销会话的同时，把该设备在准入设备上登记的 **MAC 免认证绑定**一并解除。
绑定没了，设备自然不会再被自动拉上线。

`action=logout` 只注销 RADIUS 会话，不动 MAC 绑定，
于是准入设备发现这台设备的流量后立刻按 MAC 重新认证——用户完全无感。

---

## 3. 对产品的影响与决定

| 项 | 决定 |
| --- | --- |
| 一键下线（本机） | **默认用 `rad_user_dm`（unbind=1）**，即"踢自己" |
| 配置项 | `behavior.logout_method`：`dm`（默认）或 `portal` |
| 关机自动下线 | 同样用 `dm`，否则关完机名额还在 |
| 腾位（踢别的设备） | 本来就是 `rad_user_dm`，不受影响 |

副作用与说明：

- `unbind=1` 会解除该设备的 MAC 免认证绑定。对"要腾出名额"这个目标来说正是所需；
  用户下次登录时会重新建立绑定。
- 如果用户**希望保留无感知认证**（希望设备一直自动在线），把
  `behavior.logout_method` 设成 `portal` 即可——但那样"下线"就只对本次会话有效，
  设备很快会自己回来。

---

## 4. 顺带发现的两个坑

### 4.1 `rad_user_info` 会被限流

请求过密时它返回 `speed_limit_error`（"认证请求太频繁，请稍后10s重试"）。
**这不代表离线**。把"查不到"当成"离线"会导致"明明登录成功了却报告失败"。

代码里的对应设计：

- `OnlineStatus.state` 是三态（online / offline / unknown），不是布尔；
- `local_state()` 遇到未知状态时用**在线设备列表**兜底判断
  （设备列表不受该限流影响，且能直接看到本机 IP 在不在里面）；
- `wait_state()` 遇到限流按 10 秒退避，避免轮询把自己打成限流；
- `status` 命令遇到限流时提示并等 10 秒重试一次，而不是给模糊答案。

### 4.2 判断"有没有网"不能只看 HTTP 状态码

未认证时，准入设备会把 HTTP 请求拦下来返回门户页面（状态码常常还是 200）。
可靠做法是：直接测 TCP 连接（本实验用的是 `114.114.114.114:53`），
或者检查返回内容是不是门户页面。
