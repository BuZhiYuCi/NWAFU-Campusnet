## 1. 测试目标

本产品是一个**会改变服务端会话状态**的运维工具：一次"下线"会真实释放（或抢占）学校认证系统的在线名额，一次"腾位"会踢掉另一台设备。因此测试的第一目标不是"功能跑通"，而是**确认它不会在用户不知情的情况下做错事、也不会把界面卡死让人无从判断**。

按此推导出四条可验收的质量目标：

| 编号 | 目标 | 量化判据 |
| --- | --- | --- |
| G1 | 破坏性操作可预期 | 所有"下线/踢人"路径必须在执行前给出可读的确认或拒绝，且事后能明确回答"到底成没成"；不允许出现"报成功但实际仍在线" |
| G2 | 界面永不假死 | 任意网络/异常条件下，5 秒内必有一次可见的界面状态变化；20 秒内必解除忙碌态 |
| G3 | 凭据不泄露、不丢失 | 明文密码不出现在任何日志/配置文件/进程命令行；配置损坏或换机时给出可理解的提示而非静默清空 |
| G4 | 协议层可回归 | 加密与签名有参考向量；服务端字段变化时能被用例捕获，而不是"测试全绿、线上全挂" |

## 3. 测试策略（分层）

按"越靠下越便宜、越靠上越接近真实"组织，各层职责不重叠：

| 层 | 名称 | 手段 | 覆盖对象 | 现有基础 | 本轮目标 |
| --- | --- | --- | --- | --- | --- |
| L0 | 静态评审 | 人工读码 + 数据流追踪 | 所有模块 | 已完成一轮，产出 13 条缺陷（见 §6） | 缺陷复现确认 |
| L1 | 单元测试 | `unittest`，无 IO | crypto / policy / config / models / log / errors | 216 条已存在 | 补 20~25 条（空串、非 4 倍数、中文、超长、损坏配置、脏设备行） |
| L2 | 组件集成 | 本地 HTTP 桩服务器（`http.server`） | `portal._request` / 超时 / HTTPError / 非 JSONP / 重定向 | **0 条** | 新建 14 条，这是本轮最大增量 |
| L3 | GUI 驱动 | 真实 Tk 窗口 + `root.update()` 泵 | 首次向导、刷新、登录/下线、异常恢复、看门狗 | 26 条 | 补 8 条（看门狗、迟到结果、连点、托盘 marshal、保存失败） |
| L4 | CLI 端到端 | `subprocess` 调真实入口 + 桩门户 | 8 子命令、退出码、`--json` 可解析性 | 38 条（进程内） | 补 6 条进程级（编码、管道、Ctrl+C） |
| L5 | 打包冒烟 | PyInstaller 产物 + `--selftest` | 资源内嵌、windowed 崩溃、冷启动 | **0 条** | 新建 8 条检查项（半自动） |
| L6 | 手工真机 | 校园网 + 真实账号 | 真实登录/下线/腾位/限流 | 靠 `tools/verify_*.py` 人工跑 | 出可执行步骤清单，由你执行 |

> **L2 是本轮的核心补强**：现有 216 条测试里，真实 HTTP 交互覆盖为 0——`_request`、`HTTPError` 分支、超时语义、非 JSONP 降级全部没有用例。而线上故障恰恰最容易出在这一层。

## 10. 风险与不可测项（诚实声明）

1. **真实认证链路无法在我这边验证**。所有 `login/logout/kick` 的真机行为必须由你在校园网 + 真实账号下执行；我的自动化只能证明"对给定响应的处理正确"，不能证明"服务端确实接受了请求"。
2. **服务端协议漂移不可控**。用例基于 `docs/02-portal-protocol.md` 的实测样本；学校升级 SRun 后，桩数据会与线上不一致，测试仍会全绿——这是本测试方案的结构性盲区，只能靠 L6 真机用例兜底。
3. **杀软误报无法在测试环境复现**，只能记录现象。
4. **DPAPI 跨机行为**只能验证"解不开时降级合理"，无法验证"用户能自己想到重输密码"这一体验问题。
5. **GUI 用例对时序敏感**。现有 `pump()` 依赖 `sleep(0.02)+update`，在慢机/CI 上可能假失败；本轮会把硬超时改为条件轮询并记录实测耗时，但仍不保证 100% 稳定。
6. **本计划未覆盖"多人协作/服务端多设备并发"**，因为工具本身无服务端组件。
